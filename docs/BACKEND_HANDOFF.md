# 백엔드 연동 가이드

이 문서는 현재 HTML 코드를 바탕으로 한 구현 제안이다. API 경로·DB 구조·프레임워크는 확정되지 않았다. 개발 시작 전에 기존 저장소와 실행 환경을 확인하고 맞춰 적용한다.

## 1. 현재 데이터 계약

브라우저 `localStorage`에 저장되는 키와 필드다. 실제 사용자 데이터는 패키지에 포함되지 않는다.

| 키 | 현재 값 |
| --- | --- |
| `pling.events.v1` | 배열: `{id,title,date,start,end,color,done,sample?,moodTracked?}` |
| `pling.goals.v1` | 배열: `{id,title,date,done,crewId?}` |
| `pling.crews.v1` | 배열: `{id,name,goal,date,category,description,code,createdAt}` |
| `pling.coins.v1` | `{balance,claimed:["plan:<id>",...]}` |
| `pling.notifications.v1` | `{enabled,atStart,before,sound}` |
| `pling.theme.v1` | 문자열: `light` / `dark` / `system` |
| `pling.grade11-example.v1` | 문자열 `added`: 예시 재추가 방지용 |

날짜 `YYYY-MM-DD`, 시간 `HH:mm`, 색 `#RRGGBB`, Boolean 완료값. 알림 before는 0/5/10/15, 기본 enabled=false, atStart=true, before=0, sound=true. 크루의 date·description은 빈 문자열 가능. id는 로컬 생성값이며 서버의 영구 ID 전략은 별도 결정한다.

`sample`, `moodTracked`는 예시 일정과 캐릭터 표정을 구분하기 위한 현재 디자인 필드다. 서버의 실제 완료 이력은 별도 관리하고 완료 취소 정책을 명확히 한다.

## 2. 서버 모델 초안

| 자원 | 필요한 필드·관계 제안 |
| --- | --- |
| User | 인증 제공자 ID, 표시 이름, 타임존, 생성 시각 |
| Plan | 소유자, 제목, 날짜/시작/끝 또는 대응 UTC 시각, 타임존, 색, 완료 상태, 버전 |
| Goal | 소유자, 제목, 목표일, 완료 상태, 연결 크루 선택 |
| SurveyResponse | 사용자, 질문 버전, 선택 답변, 제출 시각 |
| StudyTypeResult | 사용자, 분류 규칙 버전, 유형·대표 위치, 응답 연결 |
| FocusSession | 사용자·계획, 예정 길이, 대기/실행/중지/완료/넘김, 실제 시작·완료 시각, 남은 시간 또는 일시정지 누적 |
| RewardLedger | 사용자·계획·세션·사유·5코인·지급 키·지급 시각 |
| Crew / CrewMember | 공동 목표, 목표일, 작성자, 멤버·역할, 가입 상태 |
| Invite | 크루·코드, 서버 고유성, 유효기간·취소 정책 |
| Preferences / Device | 사용자 알림 선호, 테마, 기기 토큰·권한 상태·갱신 시각 |
| Chat / ActionProposal | 사용자, 메시지, 일정 변경 제안, 확인·적용 상태, 대상 버전 |

코인 잔액은 클라이언트가 전달한 숫자를 신뢰하지 않고 원장과 서버 검증으로 계산한다. `(사용자, 계획, 보상사유)`와 같은 유일 키로 동일 계획의 1회 보상을 보장한다. 세션 재시도·동시 요청에도 중복 지급되지 않게 트랜잭션을 사용한다.

## 3. API 영역 초안

- 인증/사용자: 로그인 연결, 세션 검증, 내 프로필 조회·수정.
- 일정: 날짜 구간 목록 조회, 생성·수정·삭제, 완료·취소. 서버에서도 소유권·길이·색상·시간 겹침 검증.
- 목표: 내 목표 CRUD, 크루 공동 목표에서 개인 목표로 가져오기 시 중복 방지.
- 설문: 답변 저장/조회, 버전이 있는 유형 계산. UI의 유형 규칙과 결과를 일치시킨다.
- 집중: 세션 생성(대기), 시작, 일시정지, 재개, 완료, 넘기기. 조회로 재접속 복원.
- 보상: 완료된 계획의 보상 수령, 잔액·원장 조회. 오류 시 재시도 가능한 결과 제공.
- 크루: 생성·조회, 코드 초대·가입·탈퇴, 멤버 조회. 작성자/멤버 권한 검증.
- AI: 메시지 전송과 변경 제안 생성, 사용자의 확인 후 적용. 변경 대상에 버전 검증.
- 설정/기기: 선호 읽기·쓰기, 기기 토큰 등록·갱신·해제. 권한 상태와 알림 켬을 구분.

정확한 URL·HTTP 방식·응답 형태는 기존 서버 관례에 맞게 설계한다. 초기부터 모든 기능을 한 번에 연결할 필요는 없다.

## 4. Gemini 일정 변경과 공부 고민

사용자는 Google Gemini를 선택했다. 모델 이름·SDK·호스팅은 미정이다. API 비밀키는 서버 환경에서만 관리한다.

서버는 인증된 사용자의 **현재 타임존 기준 오늘 일정**을 조회해 대화 컨텍스트에 제공한다. 전체 다른 사용자의 일정이나 임의의 클라이언트 일정 ID에 접근하지 않는다. 현재 채팅 샘플 `todaySchedule`을 실제 데이터 계층으로 대체해야 한다.

권장 흐름: 사용자 메시지 → 서버 오늘 일정 조회 → Gemini의 구조화된 변경 제안 → 서버 스키마/소유권/겹침 검증 → UI 확인 → 확정 적용 → 일·주·월 및 진행 화면 새로 조회. 현재 UI도 ‘이렇게 변경할까?’ 후 적용 버튼을 사용한다.

말투는 선생님·부모님처럼 따뜻하되 다그치거나 낙인찍지 않는다. 입력 전 위로 인사를 유지한다. ‘학습시킬 것’은 사용자 희망 응답 성향이며 실제 파인튜닝이나 학습을 수행한 적은 없다. 시스템 지침/예시 대화 등 구현 방법은 후속 선택이다.

## 5. 일정 알림과 잠금화면

사용자는 계획 시간이 되면 푸시 알림을 보내길 원하며 전송 방식을 “ansp”라고 말했다. 기존 작업은 APNs를 뜻하는 것으로 잠정 해석했으나 확정 확인은 없다.

실제 iOS 앱이면 권한·토큰·서버 예약 및 APNs 전송을 연결해야 한다. 앱이 웹/PWA인지 네이티브인지에 따라 전달 방식은 달라진다. 정적 HTML만으로 실제 잠금화면 기능을 완성했다고 처리하지 않는다.

일정 생성·변경·삭제·완료·알림 끄기에 예약 생성/재예약/취소를 반영한다. 시간대·시각 변경과 재시도 시 중복 발송 방지, 만료된 토큰 정리가 필요하다. 정시 도착 보장 정책은 별도 결정한다.

`design/pling-lockscreen.html`은 고2 예시 7개를 오늘 날짜에 보여주는 독립 디자인이다. 실제 Plan 데이터·위젯·Live Activity와 연결되지 않았다.

## 6. 교체할 코드 지점

| 현재 함수/영역 | 연동할 책임 |
| --- | --- |
| `loadPlanner`, `persistPlanner` | API 저장소·로컬 캐시/마이그레이션 어댑터 |
| `#eventForm`, `openEventActions` | 일정 CRUD·완료 API |
| `renderCalendar`, `renderHomeWeek` | 조회 결과 기반 렌더링 유지 |
| `prepareRun`, `startRun`, `finishRun` | 서버 세션 수명주기, 수동 ▶ 시작 유지 |
| `#claimCoins`, `coinWallet` | 서버 원장 지급·잔액, 멱등 수령 |
| `computeStudyType`, `renderStudyType` | 응답 저장·분류 버전·결과 표시 |
| `getTodayScheduleContext`, 채팅 `todaySchedule`/메시지 처리 | 실제 사용자 컨텍스트·Gemini 변경 제안 |
| `#crewForm`, `openCrew`, 코드 복사 | 실제 크루/멤버/초대 API |
| `notifyPrefs`, `saveNotifyPrefs` | 서버 선호·기기 권한 분리 |
| `computeBuddyMood` | 실제 완료 이력 기반 표정 계산 |

HTML 변수와 함수는 하나의 IIFE 안에 있다. 서버 연동 과정에서 모듈로 분리할 수 있으나 화면 디자인과 사용자 동작은 기준 HTML에 맞춘다.

## 7. 권장 작업 순서

1. 기존 저장소·스택 확인, 실행 방법과 환경 변수 예시 준비. 비밀값 없는 예시만 커밋.
2. 인증·사용자 소유권·일정 CRUD 및 날짜/타임존 처리.
3. 로컬 예시를 실사용 데이터와 분리, 필요 시 사용자 승인 기반 로컬 데이터 가져오기. 코인 claimed를 서버 원장의 증명으로 사용하지 않는다.
4. 집중 세션과 보상 트랜잭션, 목표·설문 저장.
5. Gemini 컨텍스트·제안·확정 적용.
6. 실제 크루 가입/권한과 알림 발송, 네이티브 기능은 선택한 앱 플랫폼에 맞춰 구현.
7. 통합 검증 및 현행 명세서 갱신.

## 8. 검수 기준과 남은 결정

- 다른 계정의 일정·목표·크루·코인에 접근할 수 없어야 한다.
- 같은 색상 계획 2개는 가능, 같은 시간 계획의 충돌은 현재 UI 정책대로 거부한다.
- 오늘 날짜와 기준선은 한국 시간 기준으로 확인하고 날짜 경계도 시험한다. 타임존 일반화 여부는 제품 결정.
- 집중창 진입만으로 시간이 흐르지 않고 ▶를 눌러야 시작한다. 멈춤·재개·새로고침·다른 기기 복원 정책을 검증한다.
- 자동 종료/조기 완료 보상 기준을 결정한다. 같은 계획 완료 취소 후 재완료·버튼 연타·요청 재전송에도 5코인이 한 번만 지급되어야 한다.
- AI는 일정 변경을 서버 검증·사용자 확인 없이 확정하지 않는다. 저장 결과를 캘린더에 반영한다.
- 실제 초대 코드로 다른 사용자가 가입할 수 있어야 하며 로컬 코드 복사만으로 완료 처리하지 않는다.
- 알림을 끄거나 일정을 지우면 예약이 취소되어야 한다. 기기 권한 거부 상태를 처리한다.
- 백엔드 스택, 배포 대상, 재접속 중 타이머 경과 정책, 대화 저장·삭제 정책, 보상 조기 완료 정책, 크루 역할/정원/탈퇴 정책은 현재 미확정이다.
